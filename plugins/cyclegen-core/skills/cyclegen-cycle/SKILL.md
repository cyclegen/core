# CycleGen CYCLE 運営プロトコル

> 1時間1サイクルの人間-AI協働フレームワーク。AIが書く。人間は判断する。
> この型を螺旋的に積み重ねることで在文脈適応（In-Context Adaptation）が発動する。

## 3つの原則
1. **CYCLE管理**: 1時間の実行単位で区切り、目的逸脱を防ぐ
2. **ドキュメント駆動**: AIが書いて保存し、人間が判断する。成果物は常にファイルとして残す
3. **方針ファースト**: すぐに手を動かさない。まず方針と計画を整理し、全体像を見てから作業する

## PDCAフロー（CYCLE完了は必ずこの順序）
- **Plan**: CYCLE開始時。以下を**この順序で**実行する（順序を守り、ステップ1を省略しない）:
  1. **記憶の再注入 `memory_search`（必須・最初に行う）**: 作業に関連する過去の記憶を検索し、結果の `reason`（なぜこの記憶が返されたか）を利用者に伝えてから次へ進む。**利用者の指示が具体的でも省略しない**——記憶検索は意図の明確さと無関係に、過去の知見を浮上させる機構＝In-Context Adaptation（Deep Out）の本体である。飛ばすとPDCAの"殻"だけが回り"中身"（文脈再注入による認知拡張）が失われる。関連記憶が薄い新テーマでも、検索して「関連なし」を確認してから進む（実行有無をモデルの裁量に委ねない）。記憶ストア（MCP）に未接続の環境なら、その旨を明示して続行する。
  2. **目的と成果物を確認**し、作業量を **Nサイクル（約N×60分）** 形式で見積もる（例: 0.5サイクル≒30分、2サイクル≒120分）。見積もりは目安で、作業中に修正してよい。
  3. **利用者と合意してから着手する**。
- **Do**: CYCLE中の全作業（実装・調査・ドキュメント作成等） ＋ 知見の抽出・提案 ＋ ダイジェスト `_承認前` 作成 → **「Checkフェーズに入ります」と宣言して停止**
- **Check**: 人間が承認（知見の承認/修正/却下 ＋ ダイジェスト確認）
- **Action**: ダイジェスト確定（`_承認前`を削除してリネーム） ＋ `cycle_complete` ＋ 承認された知見を `memory_store` ＋ プロジェクト状態更新（＋ git管理を使う場合は git commit）

**⚠ 承認ゲート（製品コアの規律）**: 人間の承認なしに Action フェーズを実行しない。Do の最後で必ず停止する。
- **宣言必須（暗黙終了しない）**: Planで合意したDo群が完了したら、必ず「Checkフェーズに入ります」と**明示宣言**して停止する。成果物を提示しただけで宣言を省略して終えない。
- **早閉じしない（宣言粒度）**: まだ合意したDo群が残っているうちは宣言しない。宣言は「合意したDoが一通り終わったとき」に一度だけ行う（途中の小タスク完了ごとに宣言しない）。
- **init除外**: セットアップ・初期化（init）は作業CYCLEではなく、CYCLE番号もダイジェスト/承認ゲートも持たない（実作業CYCLEはCYCLE1から）。init完了は承認ゲートを通さず完了報告のみで終える。

Doフェーズの締め（作業が一通り終わったら）:
1. **知見の抽出・提案**: このCYCLEで発見された再利用可能な知見を具体的に提案する
2. **ダイジェスト `_承認前` を作成**: 簡潔なmdファイルとして残す
3. **Checkフェーズへの遷移を宣言して停止**: 「Checkフェーズに入ります。確認をお願いします。」

## ダイジェスト
- 配置: 標準のCYCLE進行ディレクトリ `CYCLE{N}_ダイジェスト.md`（日本語: `ドキュメント/91_サイクル進行/` ／ 英語: `docs/91_cycles/`。標準ディレクトリ構造を参照）
- Doフェーズでは `_承認前.md` サフィックスで作成
- Actionフェーズで `_承認前.md` → `.md` にリネームする（通常のファイル名変更でよい）
  - ⚠ **`git mv` は使わない**。`_承認前` はDoフェーズで新規作成したファイルであり、まだgitの追跡下に無いのが通常なので `git mv` は失敗する（`fatal: not under version control`）。git管理を使っている場合も、リネーム後に `git add` すれば履歴には残る

## CYCLE完了時の記憶保存（cycle_completeとセットで必ず両方）
- `cycle_complete` を呼ぶ（CYCLE完了イベント記録 ＋ 昇格候補提示）
  - **`used_memory_ids` に、このCYCLEで実際に参照・活用した記憶のIDを渡す**
    - **検索で返ってきただけの記憶は含めない。** 実際に判断や作業に使ったものだけを渡す
    - 心当たりが無ければ**空のままでよい**。数を増やすことが目的ではない
    - なぜ: 記憶ストアは「返したのに使われなかった記憶」を見つけて整理の候補にする。
      使っていないものを混ぜると、**役に立っていない記憶が役に立っているように見えて、
      いつまでも検索結果の枠を占め続ける**
- ダイジェスト内容を**意味単位に分割**し、それぞれ `memory_store`（Layer/Context付与）。1ダイジェスト＝1記憶にしない
- 利用者の思考パターンの観察があれば `memory_store`（L4-5）
- 詳細な記憶の書き方・Layer判定は Skill `cyclegen-memory` を参照

> MCP接続時は、ダイジェスト（ファイル）と `cycle_complete`（記憶ストア）を**必ず両方**実行する。ファイルは人間が読める永続記録、`cycle_complete` は構造化記録であり、役割が異なる。

## git運用（利用者がgit管理を使う場合・任意）
Actionフェーズで実行（有効化は利用者選択）:
1. `git add` で変更ファイルをステージング
2. `git commit -m "CYCLE{N}: 作業内容の要約"`（メッセージは日本語）
- 人間の承認なしに git commit しない（承認ゲートの一部）

## 品質基準
- 成果物は常にドキュメントとして残す
- 不明点は推測せず確認する
- CYCLEの目的から逸脱しない
- 再利用可能な知見が生まれたら気づきを伝える

## コンテキストリセットのルール
| 条件 | リセット | 理由 |
|------|---------|------|
| 新しいテーマのCYCLE開始 | する | 古い文脈が判断を引っ張るのを防ぐ |
| 同一テーマの連続CYCLE | しない | 直前の文脈を活かせる |
| 3 CYCLE以上連続 | する | 会話履歴がコンテキストを圧迫し品質が劣化 |
| 利用者が明示的に「続けて」 | しない | 利用者判断を尊重 |
| **★サイクル0（CYCLE0.1〜0.3）の各サイクル間** | **必ずする**（上の「同一テーマ」行の例外） | 品質維持ではなく**教育目的**——会話履歴が消えても記憶ストアから再開できることを体感させる。リセットしないと「記憶が思い出した」のか「会話が続いているだけ」なのか利用者に区別できない（Skill `onboarding` §5） |

## 標準ディレクトリ構造
CycleGenプロジェクトの推奨構造。「プロジェクトを始めたい」または init（明示起動）で、言語を確認のうえ生成する。
番号体系: **01-09**（管理・計画系）、**10-19**（アウトプット系）、**90-99**（運用・メタ系）。

**日本語**:
```
プロジェクトルート/
├── CLAUDE.md          （Codex等は AGENTS.md）
└── ドキュメント/
    ├── 01_戦略・方針      … 方針決定、ビジョン、戦略文書
    ├── 02_計画            … 作業計画書、スケジュール、CYCLE構成
    ├── 03_設計            … 設計書、アーキテクチャ、テンプレート改訂案
    ├── 04_調査            … 調査レポート、比較分析、市場調査
    ├── 05_機能要求        … FR文書、FR_INDEX
    ├── 11_成果物          … 最終納品物（提案書、要件定義書、レポート等）
    ├── 19_work            … 中間成果物、作業中のドラフト
    ├── 91_サイクル進行    … ダイジェスト、中間報告書
    └── 99_AIへの共有      … AIに参照させたいPDF・外部資料
```

**英語**:
```
project_root/
├── CLAUDE.md          (AGENTS.md for Codex etc.)
└── docs/
    ├── 01_strategy          … Vision, strategy, policy decisions
    ├── 02_plans             … Work plans, schedules, CYCLE structure
    ├── 03_design            … Design docs, architecture, template drafts
    ├── 04_research          … Research reports, comparative analysis
    ├── 05_feature_requests  … FR documents, FR_INDEX
    ├── 11_deliverables      … Final outputs (proposals, specs, reports)
    ├── 19_work              … Work-in-progress drafts
    ├── 91_cycles            … Digests, interim reports
    └── 99_ai_context        … PDFs and external materials for AI reference
```

ひな型ファイル（`_template_` プレフィックス）:
- `05_機能要求/FR_INDEX.md` — 空のインデックス
- `05_機能要求/_template_FR.md` — FRのひな型
- `91_サイクル進行/_template_ダイジェスト.md` — ダイジェストのひな型

> ディレクトリの**標準**は製品（本Skill）が定義し、利用者環境への**配置**は init スキル（明示起動）が生成する（F1 §4 P10）。
> ※ skills / hooks は**グローバル配布**（プラグイン ／ `~/.agents/` ／ `~/.codex/`）でありプロジェクト単位には置くものが無い。標準ツリーに空の `.claude/{skills,hooks}` を含めない（init が丸写ししても空ディレクトリを作らないため。CYCLE14.21 finding#4 / CYCLE14.24 修正）。
