# CycleGen サイクル0（ガイド付きオンボーディング）

> **これは初回利用者向けの助走**。`init`（配置）が終わった直後の30〜60分で、利用者に「なぜCycleGenを回すのか」を**説明ではなく体験**で伝え、記憶ストアに最初の中身が入った状態でCYCLE1へ送り出す。
> 起動: **自動**（本スキルのdescription）／**明示**（Claude Code: `/cyclegen-core:onboarding` ／ Codex: `$onboarding`）／`init` 完了報告の引き継ぎ1行。
> ※ Codexの呼び出し名は frontmatter `name: onboarding` に一致する（配置dir名ではない）。

> **⚠ サイクル0は「中身を薄くした本物のCYCLE」である。** `init` と違い、**承認ゲート・`memory_search`・ダイジェスト・`cycle_complete` を全部通す**（0系のCYCLE番号を持つ）。型を薄めると「CycleGenを体感する」という目的そのものが達成できない——体験とは型を一巡することだからである。
> initを非CYCLEにした判断（CYCLE14.26 / FR039）と矛盾しない。基準は一貫している: **initは配置作業だから非CYCLE、サイクル0は利用者のテーマを扱う作業だからCYCLE**。

## 0. 起動したら最初に判定する（既存利用者への非干渉）

本スキルは自動起動する。誤爆は**発火してから本文で抜ける**構造で受け止める。**この順序で**判定すること。

```
① 層2（利用者の CLAUDE.md / AGENTS.md）の「プロジェクト状態」を読む
   └ 「オンボーディング中（次は CYCLE0.2 / 0.3）」の進行マーカーがある
        → ★その続きから再開する（§3 または §4 へ。memory_search で前サイクルの記憶を再注入）
          ※ コンテキストリセット直後の正常系はここに入る

② マーカーが無ければ memory_status を呼ぶ
   ├ Personal Layer が 0件〜数件で、オンボーディング済みの記録も無い
   │    → CYCLE0.1（§2）から開始する
   └ すでに記憶が積まれている（＝既存利用者）
        → 「すでにN件の記憶があります。オンボーディングは初回向けですが、
           練習として回しますか？」と確認する。
           No なら Skill `cyclegen-cycle`（通常のCYCLE運営）へ引き渡して終了する
```

> **★判定の権威は「記憶の件数」ではなく「層2の進行マーカー」に置く。** リセットを挟む設計（§5）にした結果、0.2/0.3は**記憶が既に数件ある状態で起動する**。件数だけで見ると自分の続きを「既存利用者」と誤判定して拒否してしまう。
> `memory_status` は埋め込みモデルをロードしない（`embed()` 呼び出し時の遅延初期化）ため、このガードは**軽い**。`memory_search` でガードしてはならない。

## 1. 全体像（利用者に最初に示す）

```
CYCLE0.1 発散・現在地   体感: PDCAと承認ゲートの初体験    溜まる: テーマ・目的・制約
   ── ★コンテキストリセット（必須）── 会話履歴が消える
CYCLE0.2 収束・焦点     体感: ★「覚えている」の初体験      溜まる: 判断と根拠
   ── ★コンテキストリセット（必須）──
CYCLE0.3 最初の一歩     体感: 成果物が1つ手元に残る        溜まる: 実作業の記録
                                                     → 卒業 → CYCLE1へ
```

所要は各15〜30分・合計30〜60分。**3サイクル固定**（増やさない・減らさない）。

## 2. CYCLE0.1（発散・現在地）— 目安15〜20分

### Plan
1. **`memory_status` を呼び、「Personal Layer: 0件」を利用者に見せる**（＝Before の可視化。§6 の卒業時にAfterと並べる）
2. **★初回検索の待ち時間を「先に予告してから」`memory_search` を1回実行する**（0件でよい）。予告の文言は必ず**検索を打つ前**に出す:
   > 「はじめに一度だけ、記憶の検索を実行します。**初回はモデルの取得で1〜2分ほどかかることがあります**（2回目以降は一瞬です）。そのまま少しお待ちください。」

   > **★これを省略しない。** 初回は埋め込みモデルの取得でブロックし、まっさらな利用者には「固まった」としか見えない。摩擦そのものは消えないが、**「説明のない待ち」が「説明のある待ち」に変わる**。実装コストはこの1行だけで、全ツール共通に効く。
3. このサイクルでやること（テーマの言語化）を伝えて**合意してから着手する**

### Do
**3つの問いを、1問ずつ順に尋ねる**（3つ同時に聞かない＝認知負荷）:

1. いま関心を持っていることは何ですか
2. これから達成したいことは何ですか
3. いま解決したい問題は何ですか

回答から**現在地**（何を持っていて何が足りないか）を整理し、**方向性の候補を3つ**提示する。

- 書き出し先: `19_work/CYCLE0.1_現在地メモ.md`（英語構成なら `19_work/`）
- ダイジェスト `CYCLE0.1_ダイジェスト_承認前.md` を `91_サイクル進行/`（英語: `91_cycles/`）に作成

### Check
**「Checkフェーズに入ります」と宣言して停止する。** ← ここが**承認ゲートの初体験**。「AIが勝手に進まない」ことを利用者に体で理解させる場なので、**省略も早閉じもしない**。

### Action
1. ダイジェスト確定（`_承認前` を外してリネーム）
2. `cycle_complete`
3. `memory_store` **最大3件**（§7の規約に従う）
4. **層2に進行マーカーを書く**（§5-3）: `現在のCYCLE: 0.1完了 → 次は CYCLE0.2（オンボーディング中）`
5. **§5 のリセット案内を出して、このサイクルを終える**

## 3. CYCLE0.2（収束・焦点）— 目安15〜20分

> ここが**本オンボーディング最大の山場**。利用者がICA（在文脈適応）を初めて体感する。

### Plan
`memory_search` を実行する → **0.1で保存した記憶が返る**。`reason`（なぜこの記憶が返されたか）を添えて提示し、**次のことを明示的に言語化する**:

> 「私は前回の会話を覚えていません（リセットしましたね）。**いま思い出したのは、記憶ストアから返ってきた内容です。** 前回あなたが話したのは——」

> **★この言い方が要点。** リセットしたからこそ「会話が続いているだけ」ではなく「**記憶ストアが思い出した**」と帰属できる。リセットを飛ばした利用者にはこの効果が出ないので、**その場合は正直にそう伝える**（「今回は会話が残っているので、次のサイクルでぜひリセットを試してください」）。

### Do
0.1で出した候補3つを**評価軸で比較する**:

| 評価軸 | 問い |
|---|---|
| 重要度 | それが実現したら何がどれだけ変わるか |
| 実現可能性 | いまの時間・スキル・環境で手が届くか |
| 自分がやる意味 | 他の誰かではなく自分がやる理由があるか |

→ **1つに絞る**。**選んだ理由と、捨てた理由の両方を記録する**（捨てた理由が後から効く）。

- 書き出し先: `01_戦略・方針/CYCLE0.2_方向.md`（英語: `01_strategy/`）
- ダイジェスト `CYCLE0.2_ダイジェスト_承認前.md`

### Check
宣言して停止する。

### Action
1. ダイジェスト確定 → `cycle_complete` → `memory_store` 最大3件（**判断と根拠＝L4**）
2. 層2の進行マーカーを更新: `現在のCYCLE: 0.2完了 → 次は CYCLE0.3（オンボーディング中）`
3. **§5 のリセット案内を出す**

## 4. CYCLE0.3（最初の一歩）— 目安20〜30分

### Plan
`memory_search` → 0.1＋0.2の記憶が返る。**蓄積が増えていること**を提示する（「前回は2件でしたが、いまは5件返っています」）。

### Do
決めた方向で、**具体的な成果物を1つ**作る。企画メモ／調査まとめ／たたき台の資料など、**利用者のテーマ次第**でよい。「小さくても手元に残るもの」を優先する。

- 書き出し先: `11_成果物/`（英語: `11_deliverables/`）または `19_work/`
- ダイジェスト `CYCLE0.3_ダイジェスト_承認前.md`

### Check
宣言して停止する。

### Action
ダイジェスト確定 → `cycle_complete` → `memory_store` 最大3件 → **§6 の卒業処理へ**。

## 5. ★コンテキストリセットの案内（0.1・0.2のAction末尾＝必須）

**サイクル0では、各サイクルの間で必ずリセットを案内する。** 通常のCYCLE運営とは**目的が違う**:

| | 目的 |
|---|---|
| 通常のリセット（`cyclegen-cycle`） | 文脈汚染の防止＝**品質維持** |
| **サイクル0のリセット** | リセットしても記憶で再開できることを体感させる＝**教育** |

> Skill `cyclegen-cycle` のリセット表には「同一テーマの連続CYCLE → しない」という行があるが、**サイクル0はその例外**として同表に明記してある。0.1〜0.3の間では**必ずリセットを案内すること**。

### 5-1. 順序の固定 — リセットは必ず Action の完了後、次サイクルの Plan の前

```
0.1 Do → Check（承認）→ Action（ダイジェスト確定・cycle_complete・memory_store・マーカー更新）
                          ↓ ここで初めてリセット
                        リセット → 0.2 Plan（memory_search）
```

> **⚠ Action前にリセットすると、ダイジェストと記憶が保存されないまま作業が消える。** 必ずAction完了を確認してから案内する。**この順序は理由ごと利用者に伝える**（「保存が終わったので、ここで会話を消しても大丈夫です」）。

### 5-2. 案内の文言（Actionの最後に置く）

```
ここまでの記録は保存しました（ダイジェスト・記憶ストア）。
次のCYCLE0.2に入る前に、会話をリセットしてください。

　消えるもの : この会話の履歴だけ
　残るもの   : 記憶ストア・作成したファイル・CycleGenの型（毎回読み込まれます）

リセットしたら、次をそのまま入力してください:
　Claude Code : /cyclegen-core:onboarding
　Codex       : $onboarding
　（うまくいかなければ「CycleGen オンボーディング CYCLE0.2 を始めます」でも再開できます）

これは飛ばさずに行ってください。リセットしても私が前回の内容を思い出せることが、
CycleGenの中核（記憶の再注入）を体感する一番わかりやすい形です。
```

- **リセットの実行コマンドは Skill `cyclegen-ops` に委譲する**（Claude Code は `/clear`、他ツールは各相当）。**本スキルで再定義しない**——正本は ops 側にあり、ツールごとの言い方の差もそこで吸収する。案内時は ops の「コンテキストリセットの実行」節を参照して、利用者が使っているツールの言い方で伝えること。
- 「消えるもの／残るもの」の正本も ops 側。上の枠は**要点の写し**である。
- **★再開の一言をコピペで渡すのが要点。** 初心者はリセット後に「何と言えばいいか」で止まる。**明示起動を主、自然言語を副**に置く（確実に戻れることを最優先する）。

### 5-3. 再開契約 — リセットを跨いで再開できる状態を、前サイクルのActionで必ず作る

リセット後にAIが持っているのは次の4つだけである。ゆえに0.1・0.2のActionは**この4つに再開情報を書き切ることが義務**になる。

| リセット後に残るもの | サイクル0が書き込む内容 |
|---|---|
| 層2（利用者 `CLAUDE.md` / `AGENTS.md`） | **進行マーカー**: `現在のCYCLE: 0.1完了 → 次は CYCLE0.2（オンボーディング中）` |
| 記憶ストア | そのサイクルで保存した最大3件（§7） |
| ダイジェスト（`91_サイクル進行/CYCLE0.x_ダイジェスト.md`） | 決めたこと・次にやること |
| Skill / hook（毎回再ロード） | 型そのもの（＝本スキル本文＝再開手順） |

> **★これは「会話履歴に依存せず、層2＋記憶＋ファイルで文脈を持ち回る」というCycleGenの設計そのものを、利用者自身の初日で実演している。**

## 6. 卒業（0.3のAction末尾）

1. **`memory_status` を再度呼び、「Personal Layer: 0件 → N件」を並べて見せる**
2. ここまでで体験した型を**3行**で振り返る:
   - **Plan** = 記憶の再注入（前回までを思い出すところから始まる）
   - **Do** = AIが書く
   - **Check** = あなたが判断する（承認しない限り先へ進まない）
3. 「**ここからは CYCLE1 です。** 次からは『CYCLEを始めます』または `/cyclegen-core:cyclegen start`（Codex: `$cyclegen start`）で開始してください」と伝える
4. 層2の「プロジェクト状態」に `現在のCYCLE: 0.3完了（次はCYCLE1）` を書き込み、**オンボーディング中のマーカーを消す**（§0の判定が0.3を再開してしまわないように）

> **★1. が本スキルで最も費用対効果が高い一点。** 「0件 → N件」の対比は、CycleGenの価値（蓄積の複利）を**説明ではなく実演**で伝える最短経路であり、コストは `memory_status` の2回呼び出しだけである。

## 7. 記憶保存の規約（本番検索を濁さないための線引き）

### 7-1. 保存してよいもの／してはいけないもの

| | 例 | 判断 |
|---|---|---|
| **保存する** | 利用者のテーマ・目的・制約／選んだ方向と根拠／作った成果物の要点 | ✅ **利用者固有の文脈**＝将来の検索で本当に効く |
| **保存しない** | 「CycleGenはPDCAで回す」「承認ゲートとは〜」等の**CycleGenの使い方** | ❌ **製品知識はSkillが持っている**。記憶に入れると全利用者のストアに同じ内容が重複し、初日から検索結果を製品説明が占める＝**濁りの正体はこれ** |

> **原則**: サイクル0が溜めるのは「**利用者のテーマの記憶**」であって「**CycleGenの操作の記憶**」ではない。

### 7-2. 付与規約

| 項目 | 規約 |
|---|---|
| 件数 | 各0.xで**最大3件**（計10件以下）。少なく確実に |
| タグ | `onboarding` ＋ `cycle:CYCLE0.1`（後から一括で見分け・削除できるように） |
| Layer | テーマ・目的・スコープ＝**L2** ／ 判断と根拠＝**L4** ／ 作業記録＝**L1** |
| Context | 0.1・0.2＝`planning`（テーマにより `strategy`）／0.3＝作業内容に応じて |
| Priority | **指定しない**（0.5自動）——利用増進モデルに委ねる |

> `onboarding` タグを付けておけば、利用者が後で「最初の練習分を消したい」と言ったときに `memory_archive` で一掃できる。**退路があるから安心して溜められる。**
